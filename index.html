Collaboration Model

Cara kolaborasi

Satu developer pegang satu fitur dari depan sampai belakang.

Jangan pecah ownership jadi tim frontend versus backend untuk fitur yang sama. Satu developer atau agent memegang satu vertical slice: UI, API, business logic, data, dan test sampai fiturnya benar-benar selesai.

Git Workflow

Branching

Satu fitur wajib punya satu branch sendiri.

Developer cukup bekerja dan push ke branch fiturnya. Tech Lead yang menggabungkan ke staging, lalu QA menguji hasil integrasi sebelum perubahan boleh masuk ke main/production.

Yang sering kelewat: feature branch harus short-lived, staging/main protected, PR wajib review + status checks, dan jangan force-push ke shared branches.

Release Strategy

Release

Tag release supaya versi yang sudah jalan bisa dilacak dan di-rollback.

Gunakan GitHub Releases + immutable Git tag untuk setiap versi yang benar-benar dilepas. Simpan changelog dan artifact/build identity agar tim tahu persis source mana yang menghasilkan versi tersebut.

Web: rollback biasanya lebih cepat karena server bisa redeploy versi sebelumnya. Tapi tetap penting saat ada migration, config, cache, atau perubahan API yang membuat rollback tidak sesederhana mengganti commit.
Why native makes releases criticalrollback reality
Web deployment

Tim mengontrol server dan biasanya bisa redeploy known-good build dalam hitungan menit.

Native app

Binary sudah tersebar ke device pengguna. Kita tidak bisa menarik dan menggantinya seketika.

Store delay

App Store/Play Store review dan rollout membuat hotfix tidak selalu langsung sampai ke pengguna.

Multiple versions live

Backend harus tetap kompatibel karena pengguna bisa menjalankan beberapa versi aplikasi sekaligus.

Release checklist yang jangan kelewat: semantic/versioned tag, changelog, signed/native artifacts bila relevan, migration compatibility, phased rollout, monitoring, dan known-good rollback target.

Native Deployment

Native app

Native bukan sekadar deploy. Kita mendistribusikan binary ke device yang tidak kita kontrol.

APK/AAB/IPA harus ditandatangani, diuji sebagai artifact final, lalu masuk internal/beta track sebelum production rollout. Setelah binary tersebar, user dapat berada di banyak versi sekaligus.

Rollback native tidak instan. Kita tidak bisa menarik binary yang sudah terpasang seperti mengganti container server. Biasanya recovery dilakukan lewat feature flag, server-side mitigation, atau merilis binary baru.

Incident & Rollback

Kalau production rusak

Stabilkan user dulu. Investigasi bisa menyusul.

Kalau critical flow rusak atau indikator produksi melewati batas aman, jangan terpancing memperbaiki langsung di production bila rollback lebih cepat dan aman.

Rollback trigger:
Critical journey gagal, error spike, crash, severe latency, data-integrity risk, atau dependency failure yang tidak bisa ditoleransi.
Incident & Rollbackproduction operations
01Detect

Alert/monitoring menunjukkan regression atau outage.

02Decide quickly

Bandingkan risiko rollback versus hotfix/roll-forward.

03Rollback first

Promote known-good artifact bila itu jalur recovery paling aman.

04Protect data

Pastikan migration/data change tidak membuat rollback destruktif.

05Communicate

Catat impact, owner, status, dan keputusan recovery.

06Postmortem

Setelah stabil: root cause, correction, prevention, runbook update.

Backup & Restore

Operational safety

Backup yang belum pernah direstore belum terbukti berguna.

Backup bukan sekadar file tersimpan. Tentukan apa yang dibackup, retention, recovery target, akses, enkripsi, lalu latihan restore secara berkala.

Sebelum perubahan berisiko:
Ambil backup/snapshot sebelum destructive migration atau operasi data besar, tetapi tetap desain migration supaya aman dan reversible bila memungkinkan.
Backup & Restoreproduction operations
01Scope

Database, object storage, config penting, keys sesuai policy.

02Retention

Daily/weekly/monthly sesuai kebutuhan dan biaya.

03Off-site / isolation

Jangan simpan satu-satunya backup di failure domain yang sama.

04Restore test

Uji restore ke environment terisolasi dan verifikasi integritas.

05RPO / RTO

Tahu berapa data yang boleh hilang dan berapa lama recovery.

06Access & audit

Batasi akses backup, encrypt, log siapa yang restore/download.

Backup→Verify→Restore Test→Ready

Principles

Design Principles

Sensio-native: minimal, precise, dan product-first.

Deck mengikuti bahasa visual Sensio: clean surfaces, hierarchy tegas, accent seperlunya, dan komponen yang terasa seperti bagian dari satu product system.

01

Product Clarity

Satu pesan utama per slide. Informasi disusun seperti UI Sensio: cepat dipindai, tegas, dan bebas noise.

02

Quiet Confidence

Gunakan surface terang, near-black text, border lembut, dan whitespace yang cukup. Profesional tanpa terasa dingin atau dekoratif.

03

System over Styling

Warna, radius, border, shadow, dan spacing mengikuti token Sensio. Variasi visual harus lahir dari sistem, bukan improvisasi per slide.

04

Presentation-safe Product UI

Komposisi tetap 16:9 dan PowerPoint-safe, tetapi treatment visualnya menyerupai product surface Sensio: modular, clean, dan mudah dibaca.

Guardrails

Visual Guardrails

Aturan yang tidak boleh dilanggar di slide berikutnya.

01

One message per slide

Setiap slide harus punya satu takeaway utama. Kalau ada dua ide besar, pecah jadi dua slide.

02

Maximum two columns

Gunakan satu kolom untuk narasi kuat atau dua kolom untuk perbandingan. Hindari layout 3–4 kolom kecuali berupa card ringkas.

03

Accent is intentional

Sensio brand #0D9488 hanya untuk emphasis, active state, key number, atau focal action. Jangan menjadikannya warna dekoratif massal.

04

No decorative noise

Hindari gradient dekoratif. Shadow harus tipis seperti Sensio; icon, ilustrasi, dan shape hanya dipakai bila memperjelas informasi atau hierarchy.

05

Whitespace is content

Jangan memenuhi canvas hanya karena masih ada ruang kosong. Ruang kosong menjaga fokus dan kualitas visual.

06

Consistency beats novelty

Jangan membuat gaya baru per slide. Gunakan pattern Sensio yang sama: clean surface, border subtle, radius 8–16 px, accent biru terkontrol, dan spacing konsisten.

Layout & Spacing

Layout System

Grid dan spacing dibuat predictable.

Semua slide berikutnya harus terasa berasal dari sistem yang sama, walaupun jenis kontennya berbeda.

Safe area
64 px horizontal · 48 px vertical. Header/footer tidak boleh dimakan konten utama.
Spacing
Gunakan kelipatan 8 px. Jarak antarseksi 24–40 px; antarelemen kecil 8–16 px.
Text width
Paragraf panjang maksimal sekitar 680–720 px. Hindari baris teks selebar slide.
Alignment
Default left aligned. Center hanya untuk title/divider atau pesan tunggal yang memang membutuhkan fokus.
Cards
Radius 8–16 px, border #E4E4E7, shadow sangat ringan. Card bukan dekorasi; hanya dipakai untuk grouping informasi.

Content Rules

Do

Bikin slide yang cepat dipahami.

✓Judul menyampaikan kesimpulan atau intent, bukan label generik.
✓3–5 poin utama per slide; jika lebih, pecah menjadi beberapa slide.

✓Gunakan diagram, screenshot, atau card hanya jika mempercepat pemahaman.
✓Highlight hanya 1–2 elemen paling penting per slide.

Don't

Hindari pola yang bikin deck terasa amateur.

×Paragraf panjang, font kecil, atau bullet sampai memenuhi seluruh canvas.
×Terlalu banyak warna, icon random, gradient dekoratif, atau shadow tebal yang tidak sesuai bahasa visual Sensio.
×Mengubah alignment, radius, warna utama, dan spacing hanya demi variasi.
×Menambahkan visual filler yang tidak membantu audience memahami pesan.
×Membuat slide berbeda total dari sistem hanya karena kontennya berbeda.
